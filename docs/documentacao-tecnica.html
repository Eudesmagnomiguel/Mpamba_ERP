Panorâmica

O Mpamba é um ERP modular multi-organização. Duas aplicações independentes, uma base de dados PostgreSQL, e quatro módulos de negócio que comunicam por eventos internos.

Simetria propositada

services/, hooks/, shared/dto/ e shared/types/ no frontend espelham os recursos do backend. Ao acrescentar um recurso, mexe-se nos mesmos quatro sítios de cada lado.

Arquitectura do backend

Camadas e responsabilidades

O percurso de um pedido é sempre o mesmo, e cada camada tem uma única responsabilidade:

HTTP
 └─ routes/       declara o caminho e encadeia os guards
     └─ controller/  lê o pedido, valida com o DTO, formata a resposta
         └─ services/   regras de negócio; é aqui que vive a decisão
             └─ prisma      acesso a dados
CamadaFazNão faz
RotaCaminho, método, guards de autenticação, subscrição, módulo e permissão.Lógica de negócio.
Controladorschema.parse(req.body), chama o serviço, devolve { data } e mapeia o erro para o código HTTP.Consultar a base de dados directamente.
ServiçoRegras, validações de domínio, transacções, emissão de eventos.Conhecer req ou res.

Os serviços não recebem o organizationId por parâmetro: leem-no do contexto (capítulo 3). É o que permite chamá-los de um controlador, de um handler de evento ou de um teste sem mudar a assinatura.

Composição das rotas

Cada módulo tem um index.ts que aplica os guards comuns uma única vez e monta os sub-routers. É aqui que se garante que nenhuma rota do módulo escapa às verificações: 

src/routes/module/accounting/index.tsrouter.use(authMiddleware);
router.use(subscriptionGuard);
router.use(moduleGuard('contabilidade'));

router.use('/accounts', accountRoutes);
router.use('/entries', journalRoutes);
router.use('/reports', reportRoutes);

Dentro de cada sub-router, a permissão concreta é declarada rota a rota com permissionGuard(PERMISSIONS.X).

Ordem das rotas

Rotas literais têm de ser declaradas antes das paramétricas. GET /accounts/pgc está acima de GET /accounts/:id; invertido, o Express leria «pgc» como um id de conta. Vale para qualquer caminho fixo que partilhe o prefixo com um parâmetro.

Serviços base

Cada módulo tem um base.service.ts com os getters de contexto, de que os serviços do módulo herdam: 

padrão de src/services/module/*/base.service.tsexport abstract class BaseAccountingService {
  protected get orgId(): string {
    const id = organizationContext.getOrganizationId();
    if (!id) throw new Error('Contexto de organização obrigatório para contabilidade');
    return id;
  }
  protected get userId(): string { /* idem */ }
}

O getter lança se o contexto estiver vazio. Isso transforma um esquecimento de configuração num erro imediato e explícito, em vez de uma consulta silenciosa a todas as organizações.

Isolamento entre organizações

Todos os dados de negócio pertencem a uma organização. O isolamento é a propriedade mais importante do sistema: uma falha aqui expõe dados de um cliente a outro.

O contexto de organização

shared/utils/organization.context.ts envolve um AsyncLocalStorage do Node. O authMiddleware lê o JWT e corre o resto do pedido dentro desse contexto: 

src/middleware/auth.middleware.tsconst payload = JwtStrategy.verify(token);
req.user = payload;

organizationContext.run(
  { organizationId: payload.organizationId || '', userId: payload.sub, roles: payload.roles || [] },
  () => next()
);

Como o AsyncLocalStorage acompanha a cadeia de chamadas assíncronas, qualquer serviço invocado dentro do pedido — por mais fundo que esteja — lê o mesmo contexto sem o receber por parâmetro. Pedidos concorrentes não se contaminam: cada um tem o seu store.

Onde o isolamento se aplica

  • Leituras — todo o findMany/findFirst de dados de negócio filtra por organizationId.
  • Escritas — o organizationId vem do contexto, nunca do corpo do pedido.
  • Acesso por id — usa-se findFirst({ where: { id, organizationId } }) e não findUnique({ where: { id } }): com o id sozinho, quem adivinhasse um UUID de outra organização acedia-lhe.
  • Referências cruzadas — ao aceitar um id no corpo (categoria, conta, cliente), confirma-se que pertence à organização antes de o usar.
Regra ao escrever código novo

findUnique({ where: { id } }) em dados de negócio é quase sempre um erro. A excepção são as entidades globais da plataforma (Plan, Module, Permission), que não pertencem a nenhuma organização.

O Super Admin da plataforma é o único caso sem organizationId. Os guards de subscrição e de módulo deixam-no passar por essa ausência, e as rotas de administração operam explicitamente sobre a organização indicada.

Autenticação

Tokens e validade

TokenValidadeNotas
Access token15mEnviado em Authorization: Bearer. Transporta sub, organizationId e roles.
Refresh token30mSegredo próprio (JWT_REFRESH_SECRET). Serve só para obter um access token novo.
Token de senha1hPasswordResetToken, persistido e de uso único.

Os prazos vêm de JWT_EXPIRES_IN e JWT_REFRESH_EXPIRES_IN. As senhas são guardadas com bcrypt.

O JWT não é a fonte de verdade das permissões

O token traz os papéis, mas o permissionGuard consulta a base de dados a cada pedido (rbacService.hasPermission). Uma permissão retirada tem efeito imediato, sem esperar a expiração do token — ao custo de uma consulta por pedido protegido.

Renovação no cliente

O apiClient (axios) injecta o token em cada pedido e, ao receber 401, renova e repete o pedido original uma vez. As renovações concorrentes são coalescidas numa só promessa: 

src/shared/utils/api.utils.tslet refreshPromise: Promise<string> | null = null;

async function refreshAccessToken(): Promise<string> {
  if (!refreshPromise) {
    refreshPromise = (async () => { /* ... */ })()
      .finally(() => { refreshPromise = null; });
  }
  return refreshPromise;
}

Sem isto, um ecrã com seis consultas em paralelo dispararia seis renovações ao expirar o token. Falhando a renovação, a sessão é encerrada e o utilizador volta a /signin.

Perfil e sincronização de sessão

GET /auth/me devolve o perfil construído da base de dados — papéis, permissões e módulos activos — e não o conteúdo do token, que não os traz actualizados. O SessionSync no layout raiz refresca o perfil ao abrir a aplicação e quando a janela ganha foco, para que uma alteração de acessos ou a activação de um módulo apareçam sem novo login.

Autorização

Quatro barreiras independentes, sempre nesta ordem. Cada uma responde a uma pergunta diferente e devolve um código próprio.

As quatro barreiras
GuardPerguntaHTTPCódigo
authMiddlewareQuem é?401—
subscriptionGuardA subscrição permite escrever?402SUBSCRIPTION_REQUIRED
moduleGuardO módulo está contratado?403MODULE_LOCKED
permissionGuardO papel autoriza esta acção?403FORBIDDEN_PERMISSION
Leitura continua, escrita bloqueia

O subscriptionGuard só bloqueia POST, PUT, PATCH e DELETE. Com a subscrição inactiva, a organização continua a consultar os seus dados — o que evita transformar um atraso de pagamento em perda de acesso ao histórico.

RBAC e perfis

O modelo é User → UserRole → Role → RolePermission → Permission. Um utilizador pode ter vários papéis e acumula as permissões de todos. As permissões são strings com a forma recurso:acção ou domínio:recurso:acção — por exemplo invoice:create, accounting:entry:create.

ROLE_TEMPLATES define os perfis criados em cada organização nova (AuthService.register chama RoleTemplateService.createRoleTemplatesForOrganization). O upsert sincroniza as permissões do papel, pelo que alterar um template afecta organizações novas — mas não as existentes, porque a função só corre no registo.

Ao alterar os templates

Acrescentar uma permissão a um ROLE_TEMPLATE não a concede a quem já existe. Para isso é preciso uma migração de dados — como a grant_customer_permissions_to_billing_roles, que concedeu customer:* a todo o papel que já tivesse a permissão de facturação equivalente.

Super Admin

O permissionGuard deixa passar sem verificação quem tenha o papel SUPER_ADMIN ou Super Administrador. É a única excepção ao RBAC, e existe para a área de administração da plataforma.

Padrões recorrentes

  • Unicidade por organização — @@unique([sku, organizationId]), @@unique([code, organizationId]). O mesmo código pode existir em empresas diferentes.
  • Desactivar em vez de apagar — isActive em quase todas as entidades. Registos com histórico associado nunca são eliminados.
  • Rasto de auditoria — userId em movimentos e lançamentos; createdAt/updatedAt em toda a parte.
  • Reversão em vez de correcção — reversedById em JournalEntry: o original mantém-se e a reversão fica-lhe ligada.
  • Marcas de alerta — overdueAlertedAt, criticalBalanceAlertedAt, expiryAlertedAt evitam que a verificação diária repita o mesmo aviso.

Integração entre módulos

Os módulos não se chamam directamente. Emitem eventos, e o IntegrationService é o único sítio que sabe ligar uns aos outros.

Event bus

shared/utils/event-bus.ts é um singleton sobre o EventEmitter do Node, com o limite de ouvintes elevado a 20 para vários módulos poderem reagir ao mesmo evento. Os nomes estão em EVENTS, para não se escreverem à mão. 

emissão, em invoice.service.tseventBus.emitEvent(EVENTS.BILLING.INVOICE_ISSUED, issuedInvoice);

Reacções

IntegrationService.init() subscreve os handlers. Cada handler verifica se o módulo de destino está activo antes de agir, e envolve cada reacção no seu próprio try/catch: 

src/services/module/integration.service.tsconst isStockActive = await SubscriptionService.isModuleEnabled(orgId, 'stock');
if (isStockActive) await IntegrationService.handleStockReduction(invoice);

O isolamento dos try/catch é deliberado: uma falha na baixa de stock não pode impedir o lançamento contabilístico da mesma factura, nem vice-versa, e nenhuma delas pode fazer falhar a emissão.

Eventos e reacções
EventoStockTesourariaContabilidade
invoice.issuedBaixa dos produtos—Clientes / Vendas / IVA
invoice.cancelledReposição do stockEstorno da entradaReversão do lançamento

Idempotência

Em serverless o mesmo evento pode ser processado mais de uma vez. Cada reacção verifica antes de escrever:

  • Stock — procura um StockMovement com a referência INV:<número> antes de dar baixa.
  • Contabilidade — procura um JournalEntry com o mesmo sourceReference (INV:, REC:, NC:, REVERSAL:).
  • Tesouraria — usa a referência do movimento pela mesma via.
Cold start em serverless

api/index.ts chama IntegrationService.init() a cada arranque a frio. Sem a guarda private static initialized, uma instância reaproveitada acumularia subscrições e o mesmo evento seria processado várias vezes — a mesma factura baixaria stock duas vezes. Ao acrescentar subscrições, mantenha-as dentro dessa guarda.

Limite conhecido

O bus é em memória e por instância. Um handler que falhe não é repetido automaticamente, e um documento emitido enquanto o módulo de destino estava inactivo não é reprocessado ao activá-lo. Para garantias de entrega seria preciso uma fila persistente.

Módulo de Contabilidade

O plano de contas segue o PGC-Angola (Decreto n.º 82/01). O ficheiro default-accounts.constants.ts é a fonte única: dele saem a semeadura, a consulta na aplicação e as contas-âncora dos lançamentos automáticos.

Plano de contas e sincronização

DEFAULT_ACCOUNTS tem ~254 contas com apenas code, name e side. A classe e o código-mãe são derivados do código, para não poderem contradizê-lo: 

accountClassOf('34.5.3')  // 3   — primeiro dígito
parentCodeOf('34.5.3')    // '34.5'
parentCodeOf('34')        // undefined — não há contas de 1 dígito no PGC

ensureDefaultAccounts(orgId) sincroniza conta a conta, e não «só se a organização não tiver nenhuma»: cria as que faltam com createMany e repara class, side e parentId agrupando as escrituras em poucos updateMany. Não toca em name nem em isActive, que são decisões da organização.

É chamado uma vez por operação — listAccounts no início, e ensurePlan no serviço de lançamentos automáticos, antes de resolver as âncoras em paralelo. Chamá-lo de dentro de getAccountId punha várias sincronizações a correr ao mesmo tempo.

Ordenação de códigos

Nunca ordenar códigos de conta como texto

ORDER BY code coloca 75.2.11 antes de 75.2.9 e 68.10 antes de 68.9. Use compareAccountCodes, que compara segmento a segmento como número. Existe no backend (default-accounts.constants.ts) e espelhado no frontend (shared/utils/accounting.utils.ts).

Validações dos lançamentos manuais

createManualEntry recusa: menos de duas linhas; débito e crédito na mesma linha; linha sem valor; lançamento não balanceado; contas de outra organização; contas desactivadas; contas que agregam sub-contas; data futura. A verificação das contas faz duas consultas — uma para as contas em si, outra para saber quais têm filhos (distinct: ['parentId']).

Arquitectura do frontend

Ler antes de escrever código

O projecto usa Next.js 16 e React 19. Há APIs e convenções que mudaram face a versões anteriores. O AGENTS.md do frontend obriga a consultar node_modules/next/dist/docs/ antes de escrever código novo, em vez de assumir o que se sabia do App Router.

Grupos de rotas e layouts

  • app/(auth)/ — login, registo, activação, recuperação de senha. Sem sessão.
  • app/(modules)/ — um directório por módulo (admin, billing, stock, treasury, contabilidade), cada um com o seu layout.tsx.
  • app/core/ — ecrãs comuns: utilizadores, papéis, subscrição, configurações, perfil.

Cada módulo declara a navegação num *.config.ts tipado como LayoutConfig: logótipo, routeLabels (usados no breadcrumb) e groups com os itens. Cada item traz a permission que o torna visível, ou null para visível sempre. 

app/(modules)/contabilidade/_components/accounting.config.ts{ name: 'Plano de Contas', href: '/contabilidade/accounts',
  icon: ListTree, permission: PERMISSIONS.ACCOUNTING_ACCOUNT_VIEW }

Acrescentar um ecrã ao menu é acrescentar uma linha aqui. A permissão tem de ser a mesma que o guard da rota exige no backend — a divergência entre as duas é o defeito mais fácil de introduzir e o mais confuso de diagnosticar (o item aparece e a acção falha com 403).

Camadas service, hook e DTO

CamadaResponsabilidade
services/Chamada HTTP e desembrulho do { data }. Sem estado.
hooks/useQuery/useMutation, chaves de cache e invalidação.
shared/dto/Esquemas zod dos formulários, via zodResolver.

As invalidações de cada módulo estão centralizadas num hooks/module/*/utils.ts, para uma mutação não deixar ecrãs vizinhos com dados velhos.

Estado e cache

  • TanStack Query — dados do servidor. Chaves em kebab-case com o id quando aplicável: ['accounting-account', id].
  • Zustand (store/auth.store.ts) — sessão: tokens e perfil. É de onde o apiClient lê o token.
  • Dados imutáveis — a referência do PGC usa staleTime: Infinity: é igual para todas as organizações e não muda entre versões.

Validação

Zod nos dois lados, com esquemas de forma equivalente mas propositadamente não partilhados: os projectos são deployados em separado e não têm um pacote comum.

LadoOndePapel
Frontendshared/dto/*.dto.tsFeedback imediato no formulário, via zodResolver.
Backendshared/dto/*.dto.tsFronteira de confiança. Valida sempre, ignorando o que o cliente já validou.

Os esquemas convivem com o que os formulários HTML realmente enviam. Dois casos que valem por si: 

input de data vazio devolve '', não undefineddate: z.preprocess(
  (value) => (value === '' || value === null ? undefined : value),
  z.coerce.date().optional()
)

Sem o preprocess, z.coerce.date() converte '' num Invalid Date e a validação falha com uma mensagem que não ajuda ninguém. 

no frontend, sem transformconst optionalExpiryDate = z.string()
  .refine((v) => v === '' || !Number.isNaN(Date.parse(v)), 'Data de validade inválida')
  .nullable().optional();
Porque não há transform no frontend

.transform() faz o tipo de entrada diferir do de saída, e o zodResolver do react-hook-form deixa de casar com o tipo do formulário — o tsc falha. As conversões ficam para o backend.

As regras que dependem de mais de um campo usam .refine() com path, para o erro aparecer no campo certo — por exemplo, a classe de uma conta ter de corresponder ao primeiro dígito do código.

Base de dados e migrações

Prisma e adaptador

Prisma 7 com o adaptador @prisma/adapter-pg. O cliente é gerado para generated/prisma (fora de node_modules) e instanciado uma única vez em config/prisma.config.ts. prisma.config.ts na raiz aponta o schema, o directório de migrações e a datasource.

Depois de alterar o schema

Corra npx prisma generate. Sem isso o tsc falha com «Property X does not exist» em campos que acabou de acrescentar — o cliente gerado ainda não os conhece.

Migrações de dados

Além das de esquema, há migrações que reescrevem dados. O padrão está em align_chart_of_accounts_pgc_angola, que renumerou o plano de contas de estrutura antiga para a do PGC:

  1. Identificar as organizações visadas por um marcador inequívoco — a conta 2432, porque códigos de 4 dígitos não existem no PGC.
  2. Desligar a hierarquia (parentId = NULL), que a aplicação reconstrói depois pelo código.
  3. Prefixar os códigos a renumerar com ~. Sem este passo intermédio, renomear 42 → 11 colidiria com o 11 antigo na unique (code, organizationId).
  4. Renumerar cada conta para o código, nome, classe e lado novos.
  5. Limpar o que deixou de fazer sentido, com guarda (NOT EXISTS sobre JournalEntryLine) para não violar chaves estrangeiras.

Renumerar mantendo a mesma linha — em vez de criar contas novas e apagar as antigas — é o que faz os lançamentos e saldos acompanharem a conta.

Comentários sem acentuação nas migrações

Os comentários dos ficheiros .sql seguem a convenção já existente no repositório e não levam acentos, para evitar problemas de codificação em ferramentas que os leiam com outra collation.

Seeds

npm run seed corre prisma/seed.ts, que orquestra prisma/seed/* por esta ordem: permissões, módulos, planos, utilizadores e organizações, subscrições, e depois dados de exemplo de tesouraria, stock e séries de facturação. É idempotente por upsert.

Janela de inconsistência

Entre o deploy do frontend e o da API há um intervalo em que a interface nova fala com a API antiga. Ecrãs que dependam de endpoints novos mostram erro nesse período. Numa alteração que mude o contrato entre os dois, deploye a API primeiro.

Só se declaram os modelos e métodos que o teste usa. O contexto é mockado porque os serviços o leem em vez de o receber.

O que vale a pena testar

  • DTOs — com o que o formulário realmente envia, campos vazios incluídos.
  • Regras de recusa — um teste por motivo de rejeição, e não um teste do «caminho feliz».
  • Integridade de constantes — chart-of-accounts.test.ts verifica que o plano não tem códigos repetidos, que cada sub-conta tem mãe declarada antes de si, e que as âncoras existem e não agregam sub-contas. Apanha erros de edição no ficheiro de constantes.
  • Funções puras — comparadores e cálculos de datas, com referência fixa em vez de new Date().
UUIDs nos testes

O z.string().uuid() do zod 4 valida a versão e a variante. '11111111-1111-1111-1111-111111111111' é recusado; use '11111111-1111-4111-8111-111111111111'.

Armadilhas conhecidas

ArmadilhaO que fazer
Permissão do menu ≠ permissão do guard O item aparece e a acção devolve 403. Foi o que aconteceu com os clientes: o menu pedia customer:view e as rotas exigiam invoice:view. Ao criar um ecrã, confirme que a constante é a mesma dos dois lados.
Rota literal depois da paramétrica /pgc tem de vir antes de /:id, senão é lido como um id.
findUnique({ where: { id } }) Fura o isolamento entre organizações. Use findFirst com organizationId.
Ordenar códigos de conta como texto ORDER BY code desordena a hierarquia. Use compareAccountCodes.
Esquecer prisma generate O tsc falha em campos novos do schema.
Subscrever eventos fora da guarda de init() Instâncias reaproveitadas acumulam ouvintes e processam o mesmo evento várias vezes.
Alterar ROLE_TEMPLATES e esperar efeito retroactivo Só afecta organizações novas. Para as existentes, escreva uma migração de dados.
Numeração por count + 1 JournalEntry.number e outros contadores usam count(...) + 1 sem índice único, pelo que podem duplicar sob concorrência. Não corrigido; a correcção passa por índice único mais repetição em caso de conflito.
Constantes de permissão sem linha na base de dados 14 constantes (user_role:*, plan_module:*, organization_module:*, role_permission:create|delete) não estão em PERMISSIONS_LIST. Nenhuma está em uso, mas um permissionGuard sobre elas falharia sempre. Semeie a permissão antes de a usar.
Permissões semeadas sem constante billing:service:* e billing:setting:update existem na base de dados mas não em PERMISSIONS. As rotas de serviços usam hoje invoice:create.
Módulo activado depois do documento emitido A integração não é retroactiva. Registe os movimentos ou lançamentos de abertura.
Validade de produto por lote Product.expiryDate é um único campo. Vários lotes com validades diferentes exigiriam uma tabela de lotes e saídas por FEFO.

git push origin main                        # frontend deploya sozinho
cd mpamba-backend && npx vercel --prod --yes   # migra e deploya a API

# confirmar que as migrações correram

Acrescentar uma permissão

  1. prisma/seed/permissions.ts — acrescentar a PERMISSIONS_LIST.
  2. src/shared/utils/rbac/permission.constants.ts — acrescentar a constante.
  3. src/shared/utils/rbac/role-templates.constants.ts — atribuir aos perfis que a devem ter.
  4. mpamba-frontend/src/shared/constants/permission.constants.ts — espelhar.
  5. Aplicar no guard da rota e no item de menu, com a mesma constante.
  6. Migração de dados, se organizações existentes a devem receber.

Acrescentar um módulo de negócio

  1. prisma/seed/modules.ts e plans.ts — registar o módulo e associá-lo aos planos.
  2. src/routes/module/<novo>/index.ts — authMiddleware, subscriptionGuard, moduleGuard('<código>').

  4. Montar em src/app.ts.
  5. Frontend: app/(modules)/<novo>/ com layout.tsx e _components/<novo>.config.ts.
  6. Reacções a eventos, se houver, em IntegrationService.init() — dentro da guarda de inicialização.
